01

Why corrections must compound

The platform can already read a client questionnaire and produce structured questions. What it cannot do is get better at reading them.

Today the loop is flat. A GBK questionnaire comes in, the extractor finds 74 questions, and some of them are wrong — a terminate condition missed here, a question text truncated there. Someone opens the review screen and hand-fixes each row. The document ships. The next GBK document arrives and needs the same 74 fixes again, because nothing was learned. Every correction is spent once and thrown away.

The correction loop changes what a correction is. Instead of editing a value, Vishal writes what is actually wrong:

The correction, in his words

“The detected text is wrong and the terminate condition wasn't identified. In this client's documents the terminate always sits in the TERM row underneath the option list, not in the question text.”

That is not a fix for question 12. It is a description of how a client writes questionnaires. The system takes it, re-reads the whole document with that knowledge, shows what changed across all 74 questions, and — once approved — remembers it against that client's format profile. The next GBK document is parsed correctly on upload, by a rule nobody had to write code for.

The people who know how GBK writes questionnaires are Vaibhav and Vishal, not me. This is the mechanism that lets their knowledge reach the parser without passing through an engineer.

02

Who gets in

This is a founders' lane, not a customer feature. It is gated on a new founder role that sits alongside the existing admin and user roles in the auth system.

  • Vaibhav and Vishal — write corrections, approve or reject resolutions inside their own domain.
  • Deepesh (admin) — everything above, plus: approve global-scope rules, and receive the proposal lane.
  • Everyone else — sees none of it. No entry point renders, and the endpoints reject.

The gate is enforced server-side on every correction endpoint, not by hiding a button. A hidden button is not access control.

03

The loop, end to end

Six steps. The numbering is real — each stage genuinely feeds the next, and a correction cannot skip one.

01

Observe

On the questionnaire review screen, every extracted question carries a “Correct this” affordance. It opens against that specific question, but the correction is not obliged to be about only that question.

Human
02

Write, with help

A plain-language instruction box, seeded with contextual suggestions drawn from the extractor's own uncertainty, a library of recurring correction shapes, and rules already accepted on this profile. See 04.

Human
03

Classify

The model reads the instruction plus full context — the source document blocks, what was extracted, the detected profile — and decides two things: which lane this belongs in, and what scope it applies at. Ambiguity always resolves downward to the safer answer.

Model
04

Resolve

Live lane: the model writes an extraction rule and re-runs extraction across the whole document under it. Proposal lane: it writes a structured change spec and stops. Nothing is committed yet either way.

Model
05

Review

A before/after across every affected question — improvements and regressions, counted and shown. Approve, reject, or send back with a note, which loops to step 03 carrying the note.

Human
06

Persist

Approval writes the rule to the profile's rule set at its declared scope, and the new extraction becomes the questionnaire's working state. Every transition is in the audit log; every rule can be switched off later.

Human
04

Writing the correction

A blank box is the wrong interface for a domain expert who isn't a prompt engineer. The instruction field arrives already knowing what is probably wrong.

Suggestions come from three ranked sources, and each is labelled so the reader knows why it is being offered:

  • Flagged — derived from the extractor's own low-confidence signals on this question. The system already knows where it was unsure; that uncertainty becomes the first suggestion. Highest value, shown first.
  • Common — a library of the correction shapes that recur in market research: missing terminate, truncated question text, options dropped or invented, wrong question type, routing not captured, scale points wrong, base or filter misread.
  • Learned — rules already accepted on this format profile, offered as precedent. If someone corrected terminates on a GBK document last month, that phrasing is available here.

Clicking a suggestion fills the box with an editable sentence. It never submits. The correction is always in their words by the time it is sent.

The detail that makes it compound

That scope row is the most important element on the screen. As the instruction is typed, the inferred scope updates live — so the moment Vishal writes something general, he sees that it will apply to every GBK document, and can widen or narrow it before sending. Without this, every correction quietly defaults to a one-off fix and the system never learns anything.

05

Two lanes, one router

Some corrections can be applied safely and immediately. Some need code. Nobody should have to decide which — the router decides, and it is biased toward caution.

Live lane

Applied on approval · reversible

  • Extraction rules — how to find terminates, question text, options, types, routing, scale points
  • Re-running extraction over the current document under a new rule set
  • Labels, help text, column order, field visibility, empty-state copy
  • Anything that only touches draft questionnaire data or presentation config

Safe because the blast radius is a draft. Nothing in fielding, quotas, or live respondent data can be reached from here, and every change is one row-flip away from being undone.

Proposal lane

Queued for engineering · not applied

  • New question types, new field kinds
  • Quota logic — least-fill routing, nested cells
  • Schema changes, new endpoints, new screens
  • Anything touching fielding behaviour or respondent-facing logic

The model still does real work here: it writes a structured change spec — what changes, where, why, expected effect, risk, and the test that should exist afterwards — and routes it to me as a tracked task.

Router bias

When the classifier is not confident, it routes to the proposal lane. A correction that should have been instant but waits for me costs an afternoon. A correction that should have waited but was applied live costs trust in the whole system. The asymmetry is not close, so the default is not close.

06

Rule scope & lifecycle

Every live-lane rule carries an explicit scope. The model infers it, the author confirms it, and it is visible before sending — never assumed silently.

ScopeApplies toApproved byTypical case
questionOne question in one documentAuthorA genuine one-off — a typo in the source doc itself
documentEvery question in this studyAuthorThis particular file has an unusual layout
profileEvery document of this client formatAuthorThe compounding case — “GBK always puts terminates in TERM”
globalAll extraction, every formatAdmin onlyA universal MR convention the parser has wrong

Rules are not an append-only pile. They live in a registry the founders can open, where each rule shows its text, scope, author, date, how many questions it currently affects, and a switch. Rules are ordered — later rules win on conflict — and reorderable. Switching one off re-runs extraction without it, so a bad rule is undone in one action rather than argued about.

Rule states: proposed → previewing → active → retired. Nothing is deleted; retired rules stay readable, because “why did we stop doing that” is a question that will be asked.

Three actions: Approve writes the rule at its scope and makes the new extraction current. Reject discards it and logs why. Send back returns it to the model with a note — “this broke Q31, that one uses a different row label” — which becomes part of the next attempt rather than a fresh start.

Re-extraction costs real model calls across every question in the document. That cost is shown before the run and the run is an explicit action, not something that fires while typing.

08

Data model

Five tables. Corrections and resolutions are kept separate so one instruction can be re-resolved several times without losing what was originally said.

corrections
  id, study_id, question_id (nullable — may be document-wide),
  author_id, instruction text, their words, anchor_json,
  suggested_from (flagged | common | learned | freeform),
  status, created_at

resolutions
  id, correction_id, attempt_no,
  lane (live | proposal),
  scope (question | document | profile | global),
  rule_text the learned rule, in prompt-ready form,
  spec_json proposal lane only,
  rationale, model, confidence, created_at

profile_rules
  id, profile_slug e.g. gbk_spec_table, rule_text,
  source_resolution_id, scope, ordinal, active,
  approved_by, approved_at, retired_at

extraction_runs
  id, study_id, trigger (upload | correction | rule_toggle),
  ruleset_hash, before_snapshot_id, after_snapshot_id,
  n_improved, n_regressed, model_calls, created_at

audit_log
  id, entity, entity_id, action, actor_id,
  before_json, after_json, at

Correction status machine: drafted → classified → resolved → in_review → approved | rejected | revising, with revising looping back to classified carrying the reviewer's note. Approved live-lane corrections continue to applied; approved proposals continue to queued.

09

What existing code changes

Less than it sounds. The path from a detected format to the extraction prompt already exists — it was built in T32 and it currently carries a choice where it now needs to carry content.

Today the chain runs detect_profile() → profile_hint → build_extraction_prompt(), threaded through extractor.py and schema.py. But profile_hint is a closed set of three selectors — field_spec, prose, conservative — each picking a canned guidance block. It selects; it does not carry.

The change is to widen that one seam:

  • profiles.py — the static REGISTRY gains a companion lookup for learned rules, read from profile_rules by slug, ordered, active only.
  • schema.py — build_extraction_prompt() takes the selector plus a rule list, and appends the rules as explicit instructions after the canned block.
  • extractor.py — extract_survey_definition() accepts a rule set and passes it down; re-extraction under a candidate rule set is the same call with a different list.
  • New — api/routes/corrections.py, the founder role and gate, and the review UI on QuestionnairePage.tsx.
Design property worth keeping

A profile with no learned rules must produce byte-identical output to today. That was the guarantee T32 shipped with — the profile step is never allowed to make an unrecognised document worse — and the rule layer inherits it. An empty rule list is a no-op, so the loop can ship without putting existing extraction at risk.

Build order

Each phase is independently useful and independently demonstrable. If work stops after any one of them, what exists still works.

P1

The lane and the box

Founder role, server-side gate, correction capture on the review screen, storage, and a list view. No model yet — corrections just get recorded and read.

Proves the loop
P2

Suggestions

The three suggestion sources and the live scope-inference chip. Valuable before any resolution exists, because it is what makes corrections well-formed in the first place.

Quality of input
P3

Classify and resolve

The router, the two lanes, rule generation, and the widened profile_hint seam. Re-extraction runs against a candidate rule set into a snapshot, not into the live questionnaire.

The engine
P4

Review and approve

Before/after across all questions with regressions surfaced first, the three actions, and send-back looping with the reviewer's note. Approval persists the rule.

The gate
P5

Registry and audit

Rule registry with ordering and switches, full audit trail, one-action revert, and the proposal queue on my side.

11

Risks and limits

Stated plainly, because the ones that sink a system like this are the ones nobody wrote down.

A rule can make things worse

A confidently-worded correction can degrade questions it was never about. Mitigation: regressions counted and listed first, approval impossible without seeing them, one-action revert.

Rules accumulate and contradict

Twenty rules on one profile will eventually disagree, and the prompt bloats. Mitigation: explicit ordering with later-wins, an active switch per rule, and a review prompt once a profile passes a rule count threshold.

The model misclassifies the lane

Something structural gets treated as safely-live. Mitigation: the live lane is architecturally incapable of touching fielding or respondent data — it is confined to draft extraction and presentation config, so a misroute is wrong, not dangerous.

Re-extraction is not free

Every rule preview costs model calls across the whole document. Mitigation: cost shown before the run, explicit trigger, snapshot reuse when the rule set is unchanged.

Two founders, one profile

Vaibhav and Vishal can correct the same format concurrently and overwrite each other's intent. Mitigation: P1 accepts last-write-wins on rule ordering and shows who wrote what; proper locking is deferred, not pretended.

Scope is only as good as the inference

If the scope chip guesses wrong and is not read, rules land too wide or too narrow. Mitigation: scope is confirmed on the send action, shown again on the review screen, and global scope requires admin.

12

Where this generalises

The questionnaire parser is the right first surface because it is where the platform is most obviously fallible and where the founders' knowledge is most obviously superior to mine. But the loop is not specific to it.

The same four pieces — a plain-language correction, a scope, a model-written rule, an approved before/after — apply anywhere the system makes a judgement a researcher could correct: verbatim codeframe generation, QC thresholds for speeders and straightliners, crosstab banner construction, data-map to questionnaire linking. Each of those is currently a fixed heuristic that a domain expert could improve and cannot reach.

Building it once, properly, on the questionnaire surface is what makes the other four cheap.

The line for the pitch

Most research platforms make you conform to how their parser reads a document. This one learns how your documents are written — from the researchers who write them, not the engineers who built it. Every correction is permanent and applies to every client document that follows.
