2 · How it is built

Architecture: one Postgres, four new layers

The new pieces all live in the Postgres DVV already runs: a graph of the study, vectors through the pgvector extension, a job queue and workflows, and an event stream. That means no new services to run, back up or secure at each client's site. Each layer sits behind a small Python interface, so it could move to Neo4j or Qdrant later by changing one file, if a measurement ever says Postgres is too slow.

3 · Graph database

The study graph

Every object that can explain a number becomes a node, and each "comes from" becomes an edge. Two queries cover most of what the screens need. Lineage walks upstream from a node (why is this cell 34%?). Impact walks downstream (what changes if I edit Q9?).

graph_nodes id · study_id · kind · ref · label · props(json) · version · created_at graph_edges id · study_id · src · dst · kind · props(json) · created_at unique (study_id, src, dst, kind); index (study_id, dst), (study_id, src) node kinds brief · hypothesis · question · option · variable · derived_rule data_file · cleaning_rule · cleaning_batch · weight · table · cell finding · sentence · correction · learned_rule · supplier · link edge kinds asks(question→variable) routes_to masks pipes derives measured_by(hypothesis→question) loaded_from(variable→data_file) filtered_by(cell→cleaning_batch) weighted_by(cell→weight) computed_from(cell→variable) cites(sentence→cell) corrected_by(question→correction) learned_from(learned_rule→correction)
  • Who writes it: engines write as they work. Approving the questionnaire writes question, option and variable nodes. A table run writes cell nodes, but only for cells someone opens or cites, so the graph doesn't grow to millions of rows.
  • Respondents are not nodes. A cleaning batch node keeps the list of removed IDs in its props.
  • Queries: recursive CTEs, depth-limited to 12, which run the same way on Postgres and SQLite.
4 · Vector database

Vectors: pgvector behind the store that already exists

src/engines/rag/store.py already indexes questions and verbatims, and already guards against stale text and mixed embedding models. What changes is where the vectors live: a vector(768) column with an HNSW index in production, used through one VectorStore interface.

What it is used for

  • Copilot search over a project (exists)
  • Near-duplicate open ends across respondents, for screen D
  • Answers that read like a language model: similarity to a set of known model outputs
  • Reusing corrections: "a question like this was corrected before"
  • Norms: matching a new question to past studies' questions

Rules it keeps

  • Embeddings come only from the local model (nomic-embed-text) or Bedrock, never a free tier
  • One embedding model per index; a change of model means a rebuild
  • The Postgres image changes to pgvector/pgvector:pg16. It is the same major version, so the existing data volume works unchanged.
5 · Orchestration

Jobs and workflows

Background work runs today in FastAPI BackgroundTasks (coding, translation drafts). If the server restarts, those jobs are lost, and they can't be retried or seen. They move to a job table with a separate worker. A workflow is a named list of steps with dependencies, and each step runs as a job. That makes every run resumable and visible on the rail.

jobs id · kind · study_id · payload(json) · state(queued|running|done|failed|cancelled) attempts · max_attempts · run_after · locked_by · heartbeat_at result(json) · error · workflow_run_id · step · created_by · created_at workflow_runs id · workflow · study_id · state · inputs(json) · started_at · finished_at events id · study_id · kind · data(json) · created_at (feeds SSE, kept 30 days) claim: UPDATE jobs SET state='running', locked_by=:w, heartbeat_at=now() WHERE id = (SELECT id FROM jobs WHERE state='queued' AND run_after<=now() ORDER BY created_at FOR UPDATE SKIP LOCKED LIMIT 1) RETURNING * retry: failed with attempts < max → queued, run_after = now() + 30s·2^attempts reaper: running with heartbeat older than 5 min → queued again (worker died)

field_close

Runs when the deadline passes or the quota is full.

  1. build data file
  2. verify respondents (scores)
  3. apply approved cleaning
  4. run the tab plan
  5. advanced methods
  6. draft cited report

qa_certificate

The paid QA service: a Word file in, a certificate out.

  1. extract the questionnaire
  2. expert checks
  3. simulate 1,000 respondents
  4. path coverage
  5. render the certificate PDF

verify_respondents

  1. paradata features
  2. near-duplicate open ends (vectors)
  3. score and rank
  4. write the triage list, and an event for "needs you"

learn_from_correction

  1. store the correction (graph node)
  2. propose a literal rule
  3. dry-run the rule on the last 20 studies
  4. a founder approves it, then it goes live

The product keeps its rule of one planner calling engines. The copilot reads the graph and vectors and starts workflows, and it acts only through confirmation cards. The many agents are on the build side, not in the product.

6 · Who builds it

Builder agents

The agent definitions live in .claude/agents/ in the repo. Opus plans and reviews, and Sonnet builds against a precise task card. No builder agent commits: the orchestrator runs the full test suites, ruff and the build, checks the result in the browser, and only then opens the PR. A builder's own report that something works is never taken as proof.

7 · Build queue

Tasks, in waves

Each wave's tasks run in parallel, each in its own worktree under ~/dev. The full task cards, with files, functions, acceptance tests and dependencies, are in docs/BUILD_QUEUE.md.

Wave 1 · Foundations (started now)

  • F1 Job queue, worker and workflow runner. Agent: platform-builder.
  • F2 Study graph store with lineage and impact queries. Agent: platform-builder.
  • F3 The VectorStore interface, pgvector backend and Compose image change. Agent: platform-builder.

Wave 2 · Wiring (after wave 1 merges)

  • F4 Move coding and translation drafts onto the queue; add the events table and SSE route.
  • G1 Graph writers: questionnaire approval, and cell provenance from table runs.
  • X1 Path coverage in the dry run.
  • A1 Paradata features from export columns (keystrokes, paste, timing).

Wave 3 · Screens

  • R0 The lifecycle rail and "Needs you" (screen A).
  • X2 Logic X-ray and the certificate (B).
  • T1 The Study Thread drawer (C).
  • A2 The authenticity score and session timeline (D).
  • C1 The control room (E).

Wave 4 · Insight and learning

  • R1 The citation checker.
  • R2 The cited report writer (F).
  • K1 Corrections for cleaning and table specs.
  • N1 Norms from past studies.
  • W1 The field_close and qa_certificate workflows, end to end.

Running alongside every wave, and only the founders can do it: field one real study with an outside analyst. That study is the test for whether the screens above earn their place.
