Every technique below is shaped by market-research conventions. Nine words carry most of it.

The job being replaced

A scripter reads a 40-page Word document and hand-builds the survey in Decipher or Qualtrics: types, answer lists, bases, screen-outs, masks, pipes, quotas. Days of work, and every misread line is a mistake a respondent meets. This system does that reading, and puts a person in front of the result before anyone is let in.

01The whole pipeline

One document in, one delivery out. Everything between is either deterministic code or a person deciding — the model is a narrow helper in the middle, never the spine.

02Reading the document

The central design decision: deterministic first, model last.

Questionnaires are not free prose. They are written to house conventions — a spec table with Type / Options / Base rows, a numbered question followed by an indented answer list, bracketed programmer notes like [PN: SHOW CORE BRANDS]. Conventions are parseable. So three readers run in order, and only what none of them could resolve is sent to a model.

Why not just ask a model everything?

  • Reproducibility. A reviewer who asks "why is Q14 a grid?" gets a line of the document, not a sampled token.
  • Cost and latency. Nothing is charged or awaited for the 64% a regex settles.
  • Confidentiality. Client questionnaires that never leave the server cannot be trained on by a free tier.
  • It gets better permanently. A parser fix applies to every future document; a better prompt is a coin toss each run.

A real reader: numbers that must add up

The document writes a constant-sum question as blanks. Read as an answer list it looked like a single choice between two underscores, and the data file had no column for either share.

03Shapes a parser must know

Extraction gets each question roughly right. A second family of passes runs over the whole survey, because these shapes are only visible once every question exists.

Why this matters more than it looks

Each of these was a question a respondent could not answer, or a column a client would not receive. On one real study, questions rendering blank went 11 → 1 → 0 as these passes landed. Nothing about that is model quality; it is knowing the document conventions of an industry.

04Routing as data, not code

No generated code, no eval, ever. A base is a tree, and one pure function walks it.

The trap that taught us the most

A negated screen-out — "TERMINATE if code 1 is not selected" — is stored as not(in [1]). Against an empty answer set the inner in is false, so not false is true, and every respondent was screened out on their first submit. The fix is not in the evaluator; it is a guard in front of it.

05Teaching the parser

When a reviewer sees a misread, the cheap fix is to edit that one question. The valuable fix is to teach the convention, so every future document from that client reads correctly. Both exist; the second is the product.

A taught pattern is a literal fragment — the reviewer types what they see in the document — matched by substring. Never a regex.

Why a literal, not a regex

A regex typed into a web form is an injection surface and a denial-of-service surface at once — a catastrophically backtracking pattern can hang a worker on a document that never finishes parsing. It is also a skill our reviewers should not need. "Write what you see" is a better interface and a smaller attack surface; those rarely line up so cleanly.

Patterns come in kinds — type_signal, field_alias, option_tag, randomize_signal, screen_out_range, hidden_variable — and a "Re-read all" applies the new knowledge across the whole questionnaire with no re-upload.

06Four gates before a link

The system's real promise is not "it reads documents". It is a mistake does not reach a respondent. Four independent gates stand in the way, each catching what the others cannot.

07In the field

Every rule is judged on the server. The browser renders; it never decides who qualifies.

Paradata: what the interview says besides the answers

Two things clients ask on every study that nobody can reconstruct afterwards: what device were they on, and were they really where they said. Both are recorded at entry.

A judgement, not a rule

When someone types a New York ZIP and the connection looks Californian, the interview is flagged, never dropped. A VPN, a work laptop and a neighbouring postcode are all ordinary. Silently discarding those interviews would do more damage than the fraud it is meant to catch — so the system records a verdict and lets a human decide.

08The deliverable

At approval the data map is fixed — a client asking "what columns will I get?" is answered before the first respondent, not after. At close, completes are materialised into that exact shape.

Paradata rides along as ordinary single-coded columns — vDevice, vPlaceCheck, vCountry, vRegion — so a tab plan can cut by them like any other variable.

09Search by meaning

Substring search finds "price" in a question that says price. A client asks "which question covers price sensitivity" and the document says "how much would you be willing to pay" — no word in common. Vectors close that gap.

Two lessons worth stealing

Task prefixes are behaviour, not decoration. nomic-embed-text is trained with search_document: and search_query: prefixes. Without them, a probe for "net promoter score" ranked an age question above "how likely are you to recommend". With them, every probe ranked correctly:

QueryQuestion it foundRank
price sensitivityHow much would you be willing to pay…1
net promoter scoreHow likely are you to recommend…1
brand awarenessWhich brands have you heard of?1
where the respondent livesIn which state do you live?1
packaging problemsdid not reach "the pump broke after two weeks"—

Never mix embedding spaces. Vectors from two different models are meaningless to each other, so every row stores its maker and a change of maker rebuilds rather than scoring across spaces. Each row also carries a fingerprint of the exact text it was built from: a re-read or correction rebuilds it, because a copilot quoting wording that was fixed yesterday is worse than one that says it cannot find it.

Lazy on purpose

Search is a dot product over one project's rows in Python — no vector database. A questionnaire is hundreds of chunks, not millions of documents. The code says so out loud: # ponytail: brute-force scan; move to pgvector if a project ever gets large.

10How it is tested

1,199 tests, and the names are the specification. A test is named for the behaviour a person would miss, not the function it calls:

  • Integration tests drive the real endpoints — a respondent test posts to /r/{token} like a browser would, with a phone user-agent and a forwarding header.
  • No network in the suite. Model calls are faked at one boundary; embedding tests run with no model installed, because that is the state a bare server is in.
  • Access rules are tested as behaviour: an analyst is refused respondent answers before the soft launch hits its hold, and the refusal says what would change it.

11How it ships

One Docker Compose stack per client, hosted by us: app, Postgres, Caddy for TLS, a nightly backup, optional offsite copy to S3, and an optional local model container.

Optional pieces are Compose profiles, so a client who wants no outside AI at all runs COMPOSE_PROFILES=local-ai and gets an in-house model container — same code, different posture.

The habit behind all of it

Every non-obvious decision in this codebase is written down beside the code that makes it — why a guard exists, which bug it stopped, what was measured. Six months later that comment is the difference between a fix and a regression.
